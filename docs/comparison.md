# 3개 소스 비교 분석

작성: 2026-09-19 / 대상: 차기 프로젝트 UI/UX 토대

세 소스를 같은 축으로 재어 **무엇을 가져오고 무엇을 버릴지** 정한 문서다. 결론은 §5 결정표에 있고,
그 앞은 근거다. 색 대비 수치는 전부 WCAG 2.x 상대휘도 공식으로 직접 계산한 실측값이다.

---

## 1. 소스 프로필

| | h-pms | 사내 admin 표준 (WebSquare 5) | KRDS (범정부) |
|---|---|---|---|
| 형태 | Vue 3 + Vite 운영 코드 | WebSquare 5 SPA 수집본 864파일 | 공개 디자인 시스템 (웹 + Figma) |
| 확보 경로 | 이 저장소 `frontend/` | `/Users/user/workspace/websquare-bo-ui` | [krds.go.kr](https://www.krds.go.kr/html/site/index.html) |
| 토큰 | CSS 변수 약 180개 (1층) | **0개** — 값 전부 하드코딩 | primitive/semantic 2층, `--krds` 네임스페이스 |
| 컴포넌트 | Vue SFC 30여 종 (`shared/ui`) | WebSquare 엔진 컴포넌트 + 화면 XML 141개 | 10개 범주 카탈로그 |
| 패턴 문서 | `docs/guide/ui-behavior.md` (CR-* 규칙) | 없음 (예제 화면 60개가 사실상의 문서) | 기본 패턴 11종 + 서비스 패턴 5종 |
| 테마 | 3종 (기본/프리미엄/다크) | 1종 | 라이트 + 선명한 화면 모드 |
| 접근성 근거 | 규칙 문장만 있음 ("명도 대비 확보") | 없음 | WCAG 적합성 명시, 대비비를 토큰 번호에 내장 |
| 우리 관점의 성격 | **실전 검증된 동작 규칙의 원천** | **사내 정합성의 기준점** | **체계의 교과서** |

세 소스의 쓸모가 겹치지 않는다. h-pms는 "무엇이 실제로 필요했는가", admin은 "사내에서 무엇이
표준으로 통하는가", KRDS는 "그것을 어떻게 구조화하는가"를 답한다.

## 2. 토큰 체계

### h-pms — 1층에 이름이 네 벌

`frontend/src/shared/styles/tokens.css` 한 파일에 같은 역할의 토큰이 네 계열로 쌓여 있다.

| 계열 | 예시 | 유래 |
|---|---|---|
| `--lnb-*` | `--lnb-txt`, `--lnb-muted`, `--lnb-line` | LNB v2.3 컨셉에서 시작해 전역으로 번짐 |
| `--teal` / `--ink` / `--muted` / `--line` | 로그인·테스트 화면 | 화면 단위 로컬 토큰이 전역으로 승격 |
| `--color-*` | `--color-text`, `--color-border` | 전역 토큰을 다시 만들려던 시도, 앞 계열을 참조만 함 |
| `--bg-*` / `--text-*` / `--st-*` | 내업무 가이드 v1 | 가장 최근. 앞의 셋과 겹치지 않게 **일부러 새 이름**을 씀 |

네 번째 계열 주석이 문제를 정확히 진술한다 — "기존 토큰을 지우거나 값을 바꾸면 그 토큰을 쓰는
26개 화면이 함께 회귀한다." 이름이 역할이 아니라 **출신**을 가리키기 때문에 통합이 불가능해졌다.

같은 문제가 CSS 클래스에도 있다. `layout.css`에 `.app-header`/`.hp-header`, `.tab-bar`/`.hp-tab-bar`,
`.app-shell`/`.hp-app-shell`이 나란히 살아 있다. `admin.css`와 `components.css`는 `.btn`·`.data-table`·
`.card`를 **값이 다른 두 스킨으로** 중복 정의하고 있고(`.admin-page` 9화면 대 그 밖 21화면),
프로젝트 문서가 "합치면 30개 화면에 시각 회귀"라고 적어 통합을 유보한 상태다.

### admin — 토큰 없음

CSS 커스텀 프로퍼티가 0개다. `base.css`(51KB) + `contents.css`(129KB)에 색·크기가 직접 박혀 있다.
radius만 봐도 6px 27회 · 10px 18회 · 8px 17회 · 4px 16회 · 3px 14회 · 16px 11회로 여섯 값이 섞였다.
**테마 전환·확대 대응·대비 모드가 구조적으로 불가능하다.**

### KRDS — 2층 + 번호가 약속인 스케일

`namespace > theme > category > component > type > modifier` 위계에 하이픈 구분.
핵심은 색 스케일의 **매직넘버**다 — 번호가 곧 흰 배경 대비비다.

| step | 대비비 | 용도 |
|---|---|---|
| 40 | 3:1 | 큰 글씨·아이콘·경계선의 하한 |
| 50 | 4.5:1 | 본문 글씨 하한 (WCAG AA) |
| 70 | 7:1 | AAA · 선명한 화면 모드 본문 |
| 90 | 15:1 | 최대 강조 |

이게 있으면 "이 회색 써도 되나"라는 질문이 사라진다. 번호가 답이다. 선명한 화면 모드도
팔레트를 새로 만들지 않고 **한 단계 진한 step으로 올리기만** 하면 된다.

네이밍 원칙도 명시적이다 — 외형 기반 이름 금지(`blue-button` ✕), 축약 금지(`bg` ✕ `background` ○),
상태 modifier 고정(`-default/-hover/-pressed/-focused/-disabled/-error/-active`).

## 3. 색 — 실측 대비 감사

계산 대상은 실제 소스에 있는 값이다. 기준은 WCAG AA: 본문 4.5:1, 큰 글씨·아이콘·UI 경계 3:1.

### 3-1. 브랜드 주색 위의 흰 글자

| 값 | 출처 | 흰 글자 대비 | 판정 |
|---|---|---|---|
| `#009782` | admin 주색 | 3.65 | 큰 글씨만 가능 |
| `#119a8a` | h-pms `--teal` | 3.49 | 큰 글씨만 가능 |
| `#0d7d6f` | h-pms 프리미엄 `--teal` | 5.02 | OK |
| `#0e8275` | h-pms `--teal-600` | 4.70 | OK |
| `#025347` | admin 딥 | 9.01 | OK |

**두 프로젝트의 기본 CTA 버튼이 모두 AA 미달이다.** 13px 흰 글자를 3.5:1 배경에 올리고 있다.
프리미엄 컨셉만 우연히 통과한다. 차기 프로젝트에서 기본 CTA 배경은 `#038674`(4.50) 이상을 쓴다.

두 브랜드색의 hue는 171.7°와 173.0°로 1.3° 차이다. **같은 색으로 읽힌다** — 두 계열을 유지할
이유가 없다.

### 3-2. 본문 텍스트

| 토큰 | 값 | 흰 배경 대비 | 판정 |
|---|---|---|---|
| `--lnb-txt` | `#2b2f36` | 13.44 | OK |
| `--text-default` | `#374151` | 10.31 | OK |
| `--text-muted` | `#5b6472` | 5.98 | OK |
| `--muted` (레거시) | `#7c8a92` | 3.55 | 큰 글씨만 |
| `--text-weak` | `#8b93a1` | 3.09 | 큰 글씨만 |
| **`--lnb-muted`** | `#9aa0a8` | **2.64** | **미달** |
| `--text-disabled` | `#a8aeb8` | 2.23 | 비활성만 허용 |
| admin `#999999` | — | 2.85 | 미달 |

`--lnb-muted`는 LNB 2depth 메뉴·헤더 비활성 탭·테이블 헤더·보조 텍스트에 쓰인다.
**가장 널리 쓰이는 보조 텍스트 색이 대비 미달**이다. admin `#999999`도 같다.

### 3-3. 상태 뱃지 — 두 팔레트가 갈린다

| 세트 | 글자/배경 | 대비 | 판정 |
|---|---|---|---|
| 구 `--orange` | `#f59e0b` / `#fffbeb` | 2.07 | 미달 |
| 구 `--green` | `#22c55e` / `#f0fdf4` | 2.18 | 미달 |
| 구 `--gray` | `#9aa0a8` / `#f5f6f8` | 2.44 | 미달 |
| 구 `--blue` | `#3b82f6` / `#eff6ff` | 3.38 | 미달 |
| 구 `--red` | `#ef4444` / `#fef2f2` | 3.44 | 미달 |
| 구 `--purple` | `#7c5cf0` / `#ede8fd` | 3.78 | 미달 |
| 신 `--st-test` | `#b45309` / `#fff7ed` | 4.73 | OK |
| 신 `--st-dev` | `#5b6472` / `#f4f6f8` | 5.52 | OK |
| 신 `--st-progress` | `#1d4ed8` / `#eff6ff` | 6.16 | OK |
| 신 `--st-review` | `#6d28d9` / `#f5f3ff` | 6.48 | OK |

깔끔하게 갈린다. **구 팔레트 6종은 전부 미달, 신 `--st-*` 4종은 전부 통과.** 신 계열은
"저해상도 모니터 대비 기준"으로 잡았다는 주석이 있고, 그 판단이 수치로 맞았다.
차기 프로젝트는 신 계열의 사고방식(fg/bg/bd 3종 세트 · 대비 먼저)만 가져가고 값은 스케일에서 뽑는다.

## 4. 타이포·컴포넌트·패턴

### 타이포

| | h-pms | admin | KRDS |
|---|---|---|---|
| 폰트 | Pretendard (정적 웹폰트) | Pretendard (OTF 9종 13.7MB) | Pretendard GOV |
| 본문 | 13px | 혼재 | **17px** |
| 단계 | 11/12/13/14/16/20 (6단) | `.f16`/`.f20`/`.f30` 유틸 + 하드코딩 | Display 3 · Heading 6 · Body 4 |
| 굵기 | 500/600/700/800 혼용 | 100~900 전부 로드 | **400/700 두 종만** |
| 줄간격 | 미규정 | 미규정 | **최소 150%** |
| 확대 | `--font-size-offset` 5단계 | 없음 | rem 기반 |

KRDS 본문 17px은 **대국민 서비스 기준이라 그대로 쓰지 않는다.** 업무 시스템은 한 화면에
띄우는 정보량이 우선이고, h-pms 13px에서 17px로 올리면 목록 화면 설계가 전부 무너진다.
대신 KRDS에서 **줄간격 150% 하한**과 **굵기 2종 제한**을 가져온다. 굵기 4종 혼용은 실제로
h-pms에서 강조 위계를 읽기 어렵게 만들었다(같은 13px에 500/600/700이 섞여 있다).

admin의 폰트 로딩은 그대로 베끼면 안 된다 — `font.css`가 `.otf` 파일을 `format('woff')`로
잘못 선언하고 있고, 9종 13.7MB를 전부 로드한다.

### 컴포넌트

h-pms `shared/ui` 30여 종이 실전에서 필요했던 목록 그 자체다. 특히 아래는 **다른 두 소스에 없다.**

- `HpWriteLock` — 동시 편집 잠금 표시 (낙관적 잠금 409를 화면에 드러냄)
- `HpBulkUploadModal` — 엑셀 일괄 업로드 (전건 검증 후 일괄 등록, 부분 저장 없음)
- `HpSearchFilterBar` — 조회 조건 + 상세검색 접기 + 태그형 요약
- `HpSlidePanel` — 우측 슬라이드 패널 (목록 맥락 유지하며 상세 편집)

`shared/`의 결합도가 낮다는 점도 중요하다 — 40여 파일 중 앱 스토어를 참조하는 것이 2개뿐이라
거의 그대로 떼어낼 수 있다.

admin 쪽은 WebSquare 엔진 컴포넌트(`w2:gridView` 46화면, `w2:inputCalendar` 37화면)라 코드로는
이식 불가다. 다만 `cm/template/template.xml`이 **높이를 36px 배수(72/108/144…720)로 규격화**한
점은 배울 만하다 — 화면마다 컨테이너 높이가 제각각이 되는 것을 막는다.

KRDS 컴포넌트 분류(아이덴티티 / 탐색 / 레이아웃·표현 / 액션 / 선택 / 피드백 / 도움 / 입력 /
설정 / 콘텐츠)는 카탈로그를 정리할 때 쓸 수 있는 축이다. h-pms는 `shared/ui` 평면 나열이라
"비슷한 게 이미 있나"를 찾기 어려웠다.

### 패턴

h-pms `ui-behavior.md`의 CR-* 규칙은 이 세 소스 중 **유일하게 업무 시스템 맥락에서 쓰인 규칙**이다.
KRDS 기본 패턴(입력 폼 / 오류 / 필터링·정렬 / 목록 탐색 / 확인 / 첨부파일)과 주제가 상당히 겹치는데,
겹치는 부분은 h-pms 쪽이 더 구체적이다.

| 주제 | h-pms | KRDS |
|---|---|---|
| 로딩 | 1초 미만 미표시 / 1~3초 스피너 / 문구 고정 | 일반 원칙 |
| 엑셀 업로드 | 전건 검증 후 일괄 등록, 부분 저장 없음 | 해당 패턴 없음 |
| 자동완성 | 1자 이상, debounce 300ms, 이전 요청 취소 | 일반 원칙 |
| 페이지 크기 | 20/50/100, 기본 20 | 미규정 |
| 오류 표시 | 필드 하단 빨간 문구 | + **색 외 단서 병기 요구** |
| 필수 표시 | 항목명 우측 빨간 `*` | + **스크린리더 대체 텍스트 요구** |

마지막 두 줄이 KRDS가 더 나은 지점이다. h-pms는 `*`와 빨간색만 쓰는데, 색각이상 사용자에게는
`*`만 남고 스크린리더는 "별표"로 읽거나 건너뛴다.

## 6. 남은 판단 (차기 프로젝트 착수 시 확인)

1. **대국민 접점이 있는가.** 있으면 KRDS 준수가 참고가 아니라 요구사항이 된다 — 본문 17px과
   Pretendard GOV까지 따라가야 하고, 이 문서의 결정 9번이 뒤집힌다.
2. **admin과 화면을 나눠 쓰는가.** 한 사용자가 두 시스템을 오가면 브랜드색 통일(결정 5)만으로는
   부족하고 레이아웃 셸까지 맞춰야 한다.
3. **다크 테마가 요구사항인가.** 토큰은 준비해 뒀지만(§3 [토큰](/foundations)) 화면마다 검수 비용이
   붙는다. h-pms는 3개 컨셉을 유지하느라 토큰 세 벌을 관리하고 있다.
