# 설계 원칙

토큰 문서가 **무엇이 있는가**, 컴포넌트 문서가 **무엇을 쓰는가**라면, 이 문서는
**그 값을 어디에 얼마나 쓰는가**다.

값은 이미 다 있었는데 화면이 만족스럽지 않았던 이유가 이것이다 — `--ez-space-4`가 16px인 건
알아도 *이 자리가 4인지 6인지*를 정하는 근거가 없었다. 그래서 매번 감으로 골랐고, 감은
화면마다 달랐다.

이 문서의 목표는 하나다. **새 화면이든 처음 만드는 컴포넌트든, 절차를 따르면 여백·배치·
크기가 일관되게 나오는 것.** §8과 §9가 그 절차고, 앞은 그 절차가 기대는 근거다.

§10만 성격이 다르다 — 화면 안이 아니라 **디자인 시스템과 소비 프로젝트 사이**의 규칙이다.

---

## 1. 공리 다섯

나머지 규칙이 전부 여기서 나온다. 충돌하면 이 다섯이 이긴다.

**① 값은 스케일에서만 고른다.**
임의의 px를 쓰지 않는다. 13px이 필요해 보이면 12나 16 중 하나가 맞는 것이다.
선택지를 좁히는 것이 일관성의 전부다.

**② 여백은 과하게 시작해 줄인다.**
빽빽해 보이는 화면은 거의 항상 여백이 모자란 쪽이다. 반대 방향으로 틀리는 일은 드물다.
공간을 더 주는 것이 어떤 장식보다 싸다.

**③ 흑백으로 먼저 세운다.**
위계가 흑백에서 안 서면 색을 얹어도 안 선다. 색은 위계의 마지막 한 겹이지 첫 겹이 아니다.

**④ 관계는 거리로 말한다.**
가까이 있으면 한 덩어리로 읽힌다(근접성). 선을 긋기 전에 거리로 먼저 말한다 —
여백으로 갈리는데 선까지 그으면 두 번 말하는 것이다.

**⑤ 브라우저와 싸우지 않는다.**
고정 px 폭보다 내재적 크기를, 미디어 쿼리보다 `flex-wrap`·`auto-fit`을 쓴다.
본문 폭은 글자 수(`ch`)로 잡는다 — 글자 크기가 바뀌면 같이 따라온다.

## 2. 여백 — 크기가 아니라 **역할**로 고른다

이 문서에서 가장 실효가 큰 절이다.

### 하나의 규칙

> **그룹 사이 간격 ≥ 그룹 안 간격 × 2**

같은 값이면 그룹이 보이지 않는다. 라벨과 입력이 8px 떨어져 있는데 필드끼리도 8px이면,
사용자는 어디까지가 한 필드인지 알 수 없다. 근접성 법칙을 코드로 옮기면 이 부등식이다.

**이 부등식만 지켜도 화면의 절반은 정리된다.**

### 여백 사다리

| 역할 | 어디에 | 값 | 토큰 |
|---|---|---|---|
| **헤어라인** | 스와치 띠처럼 거의 붙은 것 | 2 | `--ez-space-0-5` |
| **붙임** | 아이콘–라벨, 뱃지 내부, 단위 기호 | 4 | `--ez-gap-adjacent` |
| **항목 안** | 라벨–입력, 제목–본문, 값–증감 | 8 | `--ez-gap-intra` |
| **항목 사이** | 입력 필드끼리, 버튼끼리, 표 행 | 12~16 | `--ez-gap-inter` |
| **블록 사이** | 카드 안의 섹션끼리 | 20~24 | `--ez-gap-block` |
| **영역 사이** | 카드끼리, 조회영역–목록 | 24~32 | `--ez-gap-region` |
| **페이지** | 본문 좌우·상하 여백 | 24~48 | `--ez-layout-content-padding` |

각 단계가 앞 단계의 1.5~2배다. 옆 단계와 헷갈리면 **더 큰 쪽**을 고른다(공리 ②).

> 실제로 이 한 줄을 안 지켜서 전 화면이 한 단계씩 낮게 깔렸다(2026-09-20 감사).
> 비율(그룹 사이 ≥ 그룹 안 × 2)은 맞는데 절대값이 낮으면 화면이 눌려 보인다.

**밀도 토큰은 이 역할 토큰을 참조한다.** `--ez-card-padding` = `--ez-gap-block`,
`--ez-card-gap` = `--ez-section-gap` = `--ez-gap-region`. 같은 역할에 값이 두 벌이면
문서와 화면이 갈라진다 — 한 번 갈라졌었다.

### 파생 규칙 셋

**패딩 ≥ 내부 최대 간격.**
카드 패딩이 그 안 블록 사이 간격보다 작으면 내용이 테두리에 붙어 보인다.
카드 안에서 24px로 나눴으면 패딩도 24px 이상이다.

**여백이 충분하면 선을 긋지 않는다.**
`comfortable` 밀도에서 카드 테두리를 0으로 두는 이유다. 선과 여백을 같이 쓰면 시끄럽다.
선은 **여백을 줄 수 없을 때** 쓰는 대체재다(표 행 구분선처럼).

**수직이 수평보다 크다.**
같은 관계라도 세로 간격을 가로보다 한 단계 크게 준다. 눈이 가로로 훑고 세로로 끊기 때문이다.

### 광학 보정

수치가 맞아도 어긋나 보이면 눈을 믿는다. 흔한 경우 셋 —
아이콘 옆 텍스트(아이콘 여백이 더 커 보인다), 둥근 모서리 안쪽 패딩(더 좁아 보인다),
대문자·숫자만 있는 줄(위쪽이 비어 보인다). **보정은 예외지 규칙이 아니다.** 주석을 남긴다.

## 3. 배치 — 프리미티브로 조립한다

화면마다 레이아웃을 새로 짜지 않는다. **일곱 개 조립 부품**으로만 만든다.
새 화면에서 `position: absolute`나 일회용 margin이 나오면 부품이 모자란 것이지
예외가 필요한 게 아니다.

| 부품 | 하는 일 | 쓰는 곳 |
|---|---|---|
| **Stack** | 세로로 쌓고 간격 하나만 준다 | 페이지 뼈대, 폼, 카드 내부 |
| **Cluster** | 가로로 묶고 넘치면 줄바꿈 | 툴바, 버튼 줄, 조회 조건, 칩 |
| **Split** | 고정 비율 2열 (2:1 / 1:2) | 대시보드 위젯 |
| **Grid** | `auto-fit minmax()` 로 알아서 열 수 결정 | KPI 타일, 카드 목록 |
| **Sidebar** | 비대칭 2열, 좁아지면 쌓임 | 목록 + 상세, 마스터–디테일 |
| **Box** | 패딩 + 배경 + 경계 한 덩어리 | 카드, 패널 |
| **Center** | 최대 폭 제한 + 가운데 | 로그인, 단일 폼, 빈 상태 |

**Stack이 기본이다.** 대부분의 화면은 Stack 안에 Cluster와 Box를 넣은 것이다.

### 무게를 준다

위젯 폭이 다 같으면 무엇이 중요한지 보이지 않는다. 대시보드는 **2:1 / 1:2**로 나눈다.
균등 분할은 "전부 똑같이 중요하다"는 말인데, 그런 화면은 거의 없다.

### 본문 폭

읽는 텍스트는 45~75자에서 끊는다(`--ez-measure: 68ch`). 넘어가면 다음 줄 첫 글자를
눈이 못 찾는다. 표·그리드는 해당 없다 — 읽는 게 아니라 훑는 것이다.

## 4. 위계 — 세 축, 한 번에 둘까지

크기 · 굵기 · 색. **한 요소에 세 축을 다 쓰지 않는다.** 크고 굵고 컬러인 것은 강조가 아니라 소음이다.

| 단계 | 크기 | 굵기 | 색 |
|---|---|---|---|
| 주 | 한 단계 크게 | 700 | `--ez-text-strong` |
| 보조 | 기본 | 400 | `--ez-text-default` |
| 배경 | 기본 또는 작게 | 400 | `--ez-text-muted` |

**단계는 셋을 넘지 않는다.** 넷째가 필요하면 그 화면이 한 번에 너무 많은 걸 말하고 있다.

### 강조는 낮춰서 만든다

무언가를 띄우고 싶으면 그것을 키우기 전에 **주변을 낮춘다.** 다 키우면 아무것도 안 커진다.
대부분의 "위계가 안 보인다"는 강조 부족이 아니라 **비강조 부족**이다.

### 숫자와 라벨

숫자는 **크기**로, 라벨은 **색**으로 가른다. KPI 값을 `3xl`로 올리고 라벨을 `2xs` muted로
낮추면 위계가 크기 대비만으로 선다. 라벨까지 키우면 둘 다 죽는다.

### 한 화면에 primary 하나

주 동작 버튼은 하나다. 둘이면 사용자가 무엇이 주 동작인지 못 고른다(Von Restorff).

## 5. 타이포

- **본문 13px 고정.** 축은 '작게'가 아니라 '크게'만 있다. 12px 아래로 내려가는 선택은
  뱃지·메타(11px)까지고, 그 아래는 없다.
- **줄간격** — 본문 1.5(접근성 하한), 제목 1.3, 한 줄로 끝나는 요소 1.2.
  제목에 1.5를 주면 두 줄일 때 문단처럼 벌어진다.
- **굵기 3종**(400/500/700). 500은 UI 라벨 전용, 본문 강조는 700.
  600·800을 섞으면 강조 단계가 여섯이 되고 그러면 아무 단계도 안 읽힌다.
- **스케일 비율** — 업무 화면은 촘촘한 쪽(≈1.15)이다. 11·12·13·14·16px이 촘촘히 붙어 있고
  **숫자 단계에서만 크게 점프**한다(20 → 24 → 28 → 34). 정보는 촘촘하게, 값은 크게.
- 숫자가 열을 이루면 `font-variant-numeric: tabular-nums`. 안 주면 자릿수가 흔들린다.

## 6. 밀도 — 화면 성격이 정한다

밀도는 취향이 아니라 **그 화면에서 무엇이 가치인가**의 문제다.

| 화면 성격 | 밀도 | 왜 |
|---|---|---|
| 목록 · 그리드 · 폼 | `compact` | 한 화면에 담는 양이 가치다 |
| 대시보드 · 통계 · 상세 | `comfortable` | 훑어보는 화면, 여백이 가치다 |
| 로그인 · 빈 상태 · 마법사 | `comfortable` + 좁은 폭 | 한 번에 한 가지만 하는 화면 |

**한 화면 안에서 밀도를 섞지 않는다.** 대시보드 안의 목록 위젯도 대시보드 밀도를 따른다.

## 7. 조작 — 업무 화면에서 실제로 걸리는 것만

일반 UX 법칙 서른 개를 다 적지 않는다. 업무 시스템에서 반복해서 문제가 되는 아홉 개다.

| 원칙 | 우리 규칙 |
|---|---|
| **상태 가시성** | 1초 미만 미표시 · 1~3초 스피너. 400ms 넘으면 사용자는 "멈췄나" 생각한다 |
| **되돌릴 길** | 파괴적 동작 앞에 확인. 문구에 **무엇이 일어나는지** 적는다 |
| **오류 예방 > 오류 메시지** | 못 누르게 하는 게 누르고 나서 막는 것보다 낫다 |
| **인식 > 회상** | 코드 대신 라벨. 사용자가 코드표를 외우게 하지 않는다 |
| **Jakob** | 업무 시스템은 관례를 따른다. 새롭게 만들지 않는다 — 조회는 위, 목록은 아래, 저장은 우측 |
| **Fitts** | 자주 쓰는 동작은 크고 가깝게, 파괴적 동작은 멀리. 삭제를 저장 옆에 붙이지 않는다 |
| **Hick** | 선택지 3개 넘으면 라디오 대신 셀렉트, 10개 넘으면 검색 |
| **Chunking** | 조회 조건은 4~5개씩 묶는다. 한 줄에 여덟 개는 못 읽는다 |
| **Von Restorff** | 화면에 primary 하나. 다 강조하면 강조가 없다 |

## 8. 새 화면 만드는 절차

순서를 지킨다. 특히 **③ 이전에 색을 쓰지 않는다.**

**① 화면 유형을 고른다** → 밀도와 뼈대가 따라온다.

| 유형 | 뼈대 | 밀도 |
|---|---|---|
| 목록 | Stack[ 머리 · 조회(Cluster) · 툴바(Cluster) · 표 · 페이저 ] | compact |
| 상세 | Sidebar[ 목록 \| 패널 ] 또는 Stack[ 머리 · Grid(정보) · 이력 ] | comfortable |
| 폼 | Center[ Stack[ 섹션(Box) … · 액션(Cluster) ] ] | compact |
| 대시보드 | Stack[ 머리 · Grid(KPI) · Split(2:1) · Split(1:2) ] | comfortable |
| 마법사 | Center[ 단계 표시 · Stack(현재 단계) · 액션 ] | comfortable |

**② 흑백 블록으로 나눈다.** 색·아이콘·그림자 없이 회색 사각형만으로 배치를 세운다.
여기서 안 되면 색을 넣어도 안 된다.

**③ 블록을 프리미티브로 바꾼다.** §3의 일곱 개로만. 안 되는 블록이 있으면 배치가 틀린 것이다.

**④ 여백을 역할로 채운다.** §2 사다리에서 고르고, **그룹 사이 ≥ 그룹 안 × 2**를 눈으로 확인한다.

**⑤ 위계 3단을 세운다.** primary 하나. 강조가 안 보이면 주변을 낮춘다.

**⑥ 색을 얹는다.** 브랜드색은 액션에만, 의미색은 상태에만, 범주색은 차트에만.

**⑦ 상태 넷을 만든다.** 정상 · 빈 · 오류 · 로딩. 넷을 안 그리면 화면은 절반만 만든 것이다.

**⑧ 검사한다.** 대비(4.5:1) · Tab만으로 조작 · 200% 확대 · 색 없이 읽히는가.

## 9. 새 컴포넌트 만드는 절차

**① 이미 있나.** 컴포넌트 분류 10범주를 먼저 본다. 이름만 다른 같은 것이 제일 흔한 낭비다.

**② 네이티브로 되나.** `<select>` `<details>` `<input type="date">`는 키보드·IME·스크린리더·
모바일 동작을 이미 갖고 있다. 커스텀은 그걸 전부 다시 짜는 일이다.

**③ 두 화면 이상에서 쓰나.** 하나면 그 화면 안에 둔다. 두 번째 사용처가 생길 때 올린다.

**④ 크기 3종에 들어가나.** sm 28 / md 34 / lg 40. 밖으로 나가야 한다면 컴포넌트가 아니라
레이아웃 문제일 가능성이 높다.

**⑤ 상태 여섯을 정의했나.** default · hover · focus · active · disabled · error.
focus를 빼먹는 것이 가장 흔하다.

**⑥ 접근성 최소선.** 역할(`role`) · 이름(`aria-label` 또는 `<label>`) · 상태(`aria-*`) ·
키보드 경로. 아이콘만 있는 컨트롤에 이름이 없으면 그 컴포넌트는 미완이다.

**⑦ 토큰만 쓰는가.** hex·px 리터럴이 하나라도 있으면 테마·밀도·확대가 그 컴포넌트에서 끊긴다.

**⑧ 이름이 남의 자리를 밟지 않나.** 공개하는 클래스 이름은 소비 프로젝트의 전역 공간을
차지한다 — [§10](#_10-공개-클래스-이름은-api다)을 본다. 프리미티브 일곱과 겹치는 이름은
쓰지 않는다.

## 10. 공개 클래스 이름은 API다

여백과 위계는 화면 안의 문제고, 이 절은 **화면 밖**의 문제다. 디자인 시스템이
클래스 이름을 하나 내놓는 순간 그 이름은 소비 프로젝트의 전역 공간을 차지한다.
함수 시그니처를 바꾸는 것과 같은 무게인데, CSS라서 그렇게 취급되지 않는다.

### 이 규칙이 생긴 이유

v1.4.0에서 레이아웃 프리미티브 일곱(`.ez-stack` `.ez-cluster` `.ez-split` `.ez-grid`
`.ez-sidebar` `.ez-box` `.ez-center`)을 내놨다. 어드민 목업은 그 전부터 Tabulator
래퍼에 `.ez-grid`를 쓰고 있었다. 의존성을 올린 순간:

| | |
|---|---|
| 증상 | 표 본문 높이 **0px**. 헤더가 컨테이너 460px를 전부 먹었다 |
| 원인 | 같은 이름, 다른 뜻. 프리미티브의 `display: grid`가 표 구조를 덮었다 |
| 신호 | **없음.** 콘솔 오류 0, 타입 검사 통과, 정적 감사 통과 |

**조용히 깨진다는 것이 핵심이다.** 타입 시스템도 린터도 CSS 클래스 충돌을 모른다.
눈으로 보기 전까지 아무도 모르고, 눈으로 보는 것은 대개 사용자가 먼저다.

### 규칙 셋

**① 내는 쪽 — 공개 이름을 늘리는 것은 minor가 아니라 계약 변경이다.**
새 `.ez-*` 클래스는 변경 이력에 **이름을 나열**하고, 소비자가 대조할 수 있게 한다.
목록을 문서에 박지 않는다 — 배포물에서 읽게 한다.

```bash
grep -o '^\.ez-[a-z-]*' node_modules/@ezwel/ui/dist/layout.css | sort -u
```

**② 쓰는 쪽 — `.ez-*`를 다시 정의하지 않는다.**
뜻을 좁히거나(`.ez-datagrid`) 접두사를 분리한다(`.app-*`). 지금 안 겹친다는 것은
다음 minor에서도 안 겹친다는 뜻이 아니다.

**③ 검사를 사람에게 맡기지 않는다.**
예약어 대조는 CI에 건다. 구현은
[어드민 목업의 `audit-static.mjs`](https://github.com/hyundaiezwel/ez-admin-design-system/blob/main/scripts/audit-static.mjs)
마지막 블록에 있다 — 설치된 `layout.css`에서 예약어를 읽어 소비 쪽 CSS·SFC와 대조한다.

### 이름을 지을 때

공리 ①이 값에 대해 말하는 것을 이름에 대해서도 한다 — **선택지를 좁힌다.**

| | |
|---|---|
| 프리미티브는 **보편명**을 쓴다 | `.ez-grid` `.ez-stack`. 짧고 뜻이 하나다 |
| 그래서 소비 쪽이 쓰고 싶어 한다 | 보편명일수록 충돌 확률이 높다. 대가다 |
| 구체적인 것에는 **한정어**를 붙인다 | 표는 `.ez-datagrid`, 차트는 `.ez-chart`. 프리미티브 자리를 비워 둔다 |

## 11. 리뷰에서 묻는 다섯 가지

디자인 리뷰가 취향 논쟁이 되지 않게 하는 질문들이다. 전부 **답할 수 있어야** 한다.

1. **이 여백이 왜 이 값인가?** — §2 사다리의 어느 역할인지 말할 수 있나.
2. **그룹 사이가 그룹 안의 두 배인가?** — 아니면 왜 아닌가.
3. **흑백으로 만들어도 위계가 서는가?** — 색을 빼고 봤나.
4. **이 화면의 primary는 무엇인가?** — 하나인가.
5. **빈 상태·오류·로딩을 그렸나?** — 정상만 그린 화면은 절반이다.
