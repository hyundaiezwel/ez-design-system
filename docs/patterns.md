# 패턴 — 화면이 반복하는 것

업무 시스템 화면은 종류가 적다. 목록·상세·폼·팝업이 거의 전부이고, 그 안에서 반복되는 판단이
이 문서에 있다. h-pms `docs/guide/ui-behavior.md`의 CR-* 규칙 중 **실전에서 검증된 것**을
승계하고, KRDS 기본 패턴에서 접근성 항목을 보탰다.

---

## 1. 목록 화면

가장 많은 화면이다. 구성은 고정이다.

```
페이지 타이틀
조회 영역 (EzSearchBar)     ← 1~2줄 기본 + 상세검색 접기
툴바 (건수 · 페이지 크기 · 등록/엑셀 버튼)
표 (EzTable)
페이저 (EzPagination)
```

| 항목 | 규칙 |
|---|---|
| 페이지 크기 | 20 / 50 / 100, 기본 20 |
| 정렬 | 문자 좌 · 숫자 우 · 상태 중앙 |
| 컬럼 정렬(sort) | **제공하지 않는다.** 서버 정렬이 확정되기 전에 넣으면 페이징과 어긋난다 |
| 헤더 고정 | 세로 스크롤 시 고정 |
| 빈 상태 | "조회 결과가 없습니다." |
| 선택 행 | 배경 + 좌측 막대 두 가지로 표시 — 배경색만으로는 대비 1.1:1이라 안 보인다 |
| 조회 실패 | 인라인 배너. 토스트로 띄우지 않는다(사라지면 왜 비었는지 알 수 없다) |

부수 조회(코드·옵션) 실패는 반대로 토스트다. **목록 자체의 실패만 화면에 남긴다.**

```ts
const { rows, loading, error, reload } = useListPage(() => fetchItems(applied.value))
const { currentPage, totalPages, paged } = usePagination(computed(() => rows.value))
onMounted(reload)
```

### 조회 영역

- 기본 1~2줄 + `상세검색` 접기. **접어도 조건 값과 정렬 상태를 유지한다**(`v-show`).
- 실행: Enter(폼 기본 동작) + F2.
- 초기화 버튼은 조건만 비운다. 목록을 자동 재조회하지 않는다.
- 자동완성: 1자 이상, debounce 300ms, 300ms 안에 추가 입력이 오면 이전 요청 취소.
  공백만 입력하면 띄우지 않는다.

## 2. 입력 폼

| 항목 | 규칙 |
|---|---|
| 필수 표시 | 항목명 우측 빨간 `*` **+ 스크린리더용 "(필수)" 텍스트** |
| 오류 문구 | 필드 **하단**, 빨간색, `role="alert"` |
| 오류 표시 | 색만으로 하지 않는다 — 문구가 항상 함께 있어야 한다 |
| 읽기전용 | 회색 배경 + `readonly` (`disabled` 아님) |
| 최대 길이 | `maxlength`로 막고, 근처에 남은 글자 수를 보인다 |
| 저장 중 | 저장 버튼 비활성 (`EzButton`의 `loading`) |
| 저장 실패 | 항목별 오류는 필드 하단, 그 외는 토스트 |
| 미저장 이탈 | 확인 Alert |

서버 검증 실패를 필드에 꽂는 경로는 응답 봉투의 `error.fields`다.

```ts
try {
  await save(form)
  notify('저장했습니다', 'success')
} catch (e) {
  errors.value = toFieldErrors(e)          // { name: '이미 사용 중입니다' }
  if (Object.keys(errors.value).length === 0) notify(toMessage(e), 'danger')
}
```

### 확인 Alert

저장·삭제·이탈·승인 앞에 둔다. 문구는 **무엇이 일어나는지**를 적는다 —
"삭제하시겠습니까?"보다 "요구사항 3건을 삭제합니다. 되돌릴 수 없습니다."가 낫다.

## 3. 팝업 — 무엇을 쓸까

| 상황 | 쓰는 것 |
|---|---|
| 목록을 보면서 상세를 편집 | `EzSlidePanel` (dim 없음) |
| 목록 맥락은 필요하나 뒤를 못 만지게 | `EzSlidePanel` (dim) |
| 흐름을 끊어야 함 (확인·경고·짧은 입력) | `EzModal` |
| 팝업 위의 팝업 | `EzModal` — 패널 위에 뜰 수 있다 |

셋 다 배경 클릭으로 닫히지 않는다. 겹쳐 열려도 Esc는 **가장 위 하나만** 닫는다.

---

## 4. 상태값 — 하드코딩 금지

상태 라벨·뱃지 색을 프론트에 박지 않는다. 공통코드가 단일 원천이다.

```ts
// ✕ 컴포넌트가 업무 상태를 안다
const TONE = { COMPLETED: 'success', DELAYED: 'danger' }

// ○ 공통코드 attrs에서 내려받는다
const { label, tone } = useCode('REQUIREMENT_STATUS').get(row.status)
```

이유는 두 가지다. 상태값 세트가 도메인마다 다르고(요구사항/WBS/테스트/승인), 기획이 라벨을
바꿀 때 프론트 배포가 필요해진다.

`tone`은 `EzBadge`의 6종(`neutral`/`brand`/`info`/`success`/`warning`/`danger`) 중 하나다.
공통코드에 그 문자열을 넣는다.

## 5. 반응형·확대

업무 화면의 최소 폭은 1280px(`--ez-layout-min-width`)다. 모바일 레이아웃을 따로 만들지 않는다 —
만들면 두 벌을 유지해야 하고, 실제 사용자는 데스크톱에 있다.

대신 **브라우저 200% 확대는 지원한다**(접근성 요구). 확인 방법:

1. 1280×800에서 브라우저 200% → 논리 해상도 640×400.
2. 가로 스크롤이 두 방향으로 나면 안 된다(세로 스크롤 + 가로 스크롤 하나까지는 허용).
3. 조회 조건·버튼이 잘려서 접근 불가가 되면 안 된다.

`EzSearchBar`의 조건 영역이 `flex-wrap`인 이유가 이것이다.

## 6. 로딩·비동기

| 소요 | 표시 |
|---|---|
| 1초 미만 | 없음 |
| 1~3초 | 스피너 (`EzLoadingOverlay`, `delay` 기본 1000ms) |
| 3초 초과 | 스피너 + 진행 문구 |

전체 화면 로딩은 오버레이로 중복 클릭을 막는다. 문구는 "로딩중입니다 잠시만 기다려 주세요"로 고정.

목록 조회는 전체 화면 로딩을 쓰지 않는다 — 표 영역만 흐리거나 스켈레톤을 둔다.
화면 전체를 덮으면 조회 조건을 다시 볼 수 없다.

---

## 7. 엑셀 업로드

h-pms CR-COMP-015를 그대로 승계한다.

- 지정 템플릿만 허용.
- **전건 검증 후 일괄 등록.** 유효성 실패가 1건이라도 있으면 전체 등록 불가 — 부분 저장 없음.
- 오류는 **행 단위로** 안내한다("3행: 담당자 없음").
- 중복은 등록하지 않는다.
- 실패 시 기존 데이터를 변경하지 않는다.
- 완료 후 변경이력을 남긴다.

부분 저장을 허용하지 않는 이유 — 어디까지 들어갔는지 사용자가 알 수 없고, 재시도하면 중복이 난다.

---

## 8. 오류 메시지

| 상황 | 표시 위치 |
|---|---|
| 항목 검증 실패 | 필드 하단 |
| 목록 조회 실패 | 인라인 배너 |
| 저장·삭제 실패 | 토스트 (`danger`) |
| 권한 없음 | 화면 전체 (버튼을 숨기거나 비활성) |
| 세션 만료 | 모달 — 토스트는 놓친다 |

문구는 서버 응답 봉투의 `error.message`를 그대로 쓴다. 프론트가 코드별 문구 맵을 들지 않는다.
운영자·관리자 화면만 코드를 앞에 붙인다(`toMessageWithCode`).
